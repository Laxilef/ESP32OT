# TestAllIDs

[English](README.md)

Выберите `src_dir = examples/TestAllIDs` в `platformio.ini` репозитория,
задайте окружение своей платы и откройте монитор порта на скорости 115200 бод.
GPIO адаптера задаются через `MASTER_RX_GPIO` и `MASTER_TX_GPIO`. Включённое
окружение ESP32-S3 использует RX=35/TX=36; значения sketch по умолчанию — 4/5.

Фиксированная таблица примера содержит 101 известный стандартный ID: 87 доступных
для чтения и 14 write-only. Пример последовательно читает доступные ID из
`loop()`, может выполнять настроенные проверки записи и печатает карту доступа
и статистику. Фазы обрабатываются непосредственно в `loop()`:
`Read` → необязательная `Write` → `Report`. Фаза `Report` печатает сводку,
очищает результаты ID текущего цикла и после паузы 10 секунд начинает новый
цикл чтения. `ReadAll` остаётся отдельным примером чтения.

Каждый синхронный вызов допускает до десяти попыток всего. Успех и валидный
отрицательный ответ завершают вызов; `INVALID`, таймауты и восстанавливаемые
ошибки могут повторяться. Прикладная пауза после шага сканирования — 1 мс,
после `Report` — 10000 мс. Библиотека также обеспечивает готовность шины и
межкадровые паузы; 1 мс не является физическим интервалом между кадрами.

## Чтение и настройки по умолчанию

`TEST_ALL_IDS_ENABLE_WRITES` по умолчанию равен `0`: запросы записи не отправляются.
Запросы Status передают очищенные master enable flags, включая CH и DHW;
используйте пример там, где такие флаги допустимы.

Строка операции содержит действие, ID, имя, статус, исходный запрос и число
попыток. Полный ответ добавляет исходный кадр и тип, включая невалидные и
отрицательные ответы. Успешный payload расшифровывается через обёртку сообщения,
включая все именованные флаги и поля. ID30 сохраняет интерпретацию f8.8 библиотеки.

Группы TSP и истории ошибок читаются по индексам `0..count-1` для котла,
вентиляции/рекуперации и солнечного накопителя. Нулевое количество пропускает
группу; недоступное количество оставляет одну проверку индекса 0. Каждый
индексированный результат показывает запрошенный индекс. Строки производителя
читают символ 0.

`DATA_INVALID` и `UNKNOWN_DATA_ID` — валидные отрицательные ответы. Они отличаются
от повреждённого/несоответствующего `INVALID` и от `TIMEOUT` или `ERROR` без
полного ответа. Недоступное значение не является успешно прочитанным.

## Необязательные проверки записи

После успешной записи пары в устройстве остаётся второе значение. Проверьте
`writeValues`, прежде чем добавить этот флаг к существующим `build_flags`
выбранного окружения:

```ini
-D TEST_ALL_IDS_ENABLE_WRITES=1
```

`writeValues` содержит по одной строке для каждого из 43 записываемых ID.
Формат строки — `{enabled, first, second}`; оба значения являются объектами
`Message`, созданными через типизированные обёртки. Например:

```cpp
{
  true,
  Messages::Float::write(ID::TSet, 40.0f),
  Messages::Float::write(ID::TSet, 41.0f)
},
```

Глобальный флаг по умолчанию равен `0`, хотя 24 строки включены. Остальные
19 строк отключены: три записи OEM TSP, пятнадцать сбросов счётчиков и статус
RF-датчика. Перед использованием нужно знать их смысл для конкретного устройства;
RF-строка должна представлять датчик, действительно предоставляемый этим master.
Оба запроса должны иметь тип WRITE_DATA, одинаковый ID и разные payload.

Каждая подготовленная пара отправляется в порядке таблицы: первое значение,
применимая проверка, второе значение, применимая проверка. Значения заданы явно
для теста; отдельного чтения исходного значения и восстановления нет.

| Параметр | Заданные первое → второе значения |
|---|---|
| TSet/TsetCH2 и уставка ГВС | 40 → 41 °C |
| Максимальная уставка отопления | 50 → 51 °C |
| Комнатные уставки, передаваемые комнатные температуры и наружная температура | 20 → 21 °C |
| Максимальная относительная модуляция / управление охлаждением | 50 → 51% / 0 → 1% |
| Относительная влажность и влажность вытяжного воздуха | 50 → 51% |
| Уставка и номинальная производительность вентиляции | 30 → 31% |
| CO₂ вытяжного воздуха | 600 → 650 ppm |
| День/время, дата, год | Понедельник 12:00 → 12:01; 1 → 2 января; 2026 → 2027 |
| Конфигурация master | Флаги 0; member ID 0 → 1 |
| Режимы удалённого управления | CH OFF → NO_OVERRIDE; CH2/ГВС остаются NO_OVERRIDE, DHW push выключен |
| Версия OpenTherm master | 4.1 → 4.2 |
| Сведения о продукте master | Тип продукта 0; версия 0 → 1 |

Все приведённые температуры заданы в целых градусах Цельсия. OpenTherm 4.1/4.2 —
версии протокола. Календарные поля служат примером, а не текущими часами.
RemoteRequest — включённая пара: код BLOR 1, затем код 0 для нормальной работы
в каждом цикле с включённой записью. Отключённый RF-пример задаёт комнатный датчик
с индексом 0, нормальный заряд батареи и силу сигнала 4 → 5.

### Разрешения и ограничения температур

`prepareWriteValues` проверяет включение строки, совпадение ID, тип WRITE_DATA
и применимые разрешения. RBPflags ID 6 и 86 только читаются как источники
разрешений и никогда не записываются; перед отправкой защищены фактические ID
запросов даже при изменении таблицы. Конфигурация master с включённым SmartPower
пропускается, поскольку пример не реализует Smart Power.

| Записываемый ID | Необходимые данные и допустимый диапазон |
|---|---|
| 56: уставка ГВС | Поддержка/разрешение записи из ID6 и корректные границы из ID48; оба значения ограничиваются пересечением этих границ с 0..127 °C. |
| 57: максимальная уставка отопления | Поддержка/разрешение записи из ID6 и корректные границы из ID49; оба значения ограничиваются пересечением этих границ с 0..127 °C. |
| 1 / 8: управляющие уставки отопления | Известный MaxTSet из ID57; оба значения ограничиваются диапазоном 0..floor(min(100 °C, известный MaxTSet)). Нижняя граница ID49 к этим ID не применяется. |
| 87: номинальная производительность вентиляции | Разрешения передачи/записи из ID86. |

Если ограничение сделало обе температуры одинаковыми, второе значение заменяется
соседним с разницей 1 °C внутри разрешённого диапазона. Диапазон с единственным
целым значением пропускается. Отсутствие обязательных флагов или границ,
некорректный диапазон или недоступная пара приводят к `WRITE_SKIP`.
Корректировки выводятся как `WRITE_ADJUST`. Пригодность остальных настроенных
значений определяет пользователь.

ID56 и ID57 обрабатываются перед TSet/TsetCH2. Каждая фактическая запись ID57
помечает сохранённый максимум неизвестным; WRITE_ACK задаёт принятый максимум,
а успешное проверочное чтение уточняет его. Если последняя запись ID57 не
получила ACK, ID 1 и 8 пропускаются. Если пара ID57 пропущена, корректное
значение ID57 из обычной фазы чтения остаётся доступным.

## Проверка результата

После каждого WRITE_ACK для читаемого и записываемого ID выполняется один
синхронный `VERIFY_READ`, который читает значение и печатает именованные поля.
Для индексированных ID сохраняется записанный индекс. `WRITE_VALUE` показывает
ID, ожидаемый payload в шестнадцатеричном виде и `matched`: истина требует
READ_ACK с точным совпадением записанного payload, включая корректировки.
Проверка использует тот же максимум десять попыток, что и остальные операции.

Для write-only ID проверочного чтения нет. Успешный ACK расшифровывается через
обёртку ID; RemoteRequest выводит код запроса, код ответа и флаг принятия.
Подтверждение записи и совпадение прочитанного значения — разные результаты.
Неудачная запись не блокирует второй запрос или следующую строку таблицы;
при ошибках фактически применённое значение может оставаться неизвестным.

## Карта доступа и статистика

`Report` печатает номер цикла, состояние включения записи, общую сводку
и отдельные таблицы с рамками. Числовые счётчики выровнены по правому краю.
Итоги накапливаются с запуска, а `ID_MAP` строится заново в каждом цикле.

| Показатель сводки | Значение |
|---|---|
| `Completed calls` | Итоговые результаты синхронных вызовов после всех повторов, включая проверочные чтения. |
| `Queued attempts` | Переходы READ/WRITE в QUEUED, включая повторы; это принятые попытки, а не доказательство завершённой передачи на линии. |
| `Response frames` | Полные кадры ответов, включая невалидные и валидные отрицательные; таймаут без кадра не увеличивает счётчик. |

В `ID_MAP` поле `Protocol` показывает доступ из
таблицы; `Observed` объединяет ответы фазы чтения, подтверждения записи
и применимые разрешения протокола/устройства. `Read result` и `Write result`
показывают последний сохранённый статус; `-` означает, что направление не проверялось.

| Observed | Значение |
|---|---|
| `read/write` | Наблюдались свидетельство поддержки чтения и WRITE_ACK. |
| `read only` | Наблюдалось свидетельство чтения, а протокол или разрешения устройства запрещают запись. |
| `write only` | Получен WRITE_ACK для write-only ID протокола. |
| `not supported` | Для применимых проверенных направлений получен UNKNOWN_DATA_ID без свидетельств чтения/записи. |
| `unverified` | Применимое направление не проверено либо результат неопределённый. |

Свидетельством чтения считается READ_ACK или DATA_INVALID в фазе чтения;
пригодное значение даёт только READ_ACK. Отключённая запись, пропущенные пары и
ошибки связи не доказывают отсутствие поддержки. Если обязательные флаги
разрешений не прочитаны, соответствующие ID остаются `unverified`, а не
считаются доступными только для чтения. Карта обобщает каждый ID;
отдельные индексированные результаты сохраняют свои статусы.

Остальные разделы отчёта:

- `CUMULATIVE_STATUS`: таблица `Request status transitions` считает входы
  в каждый статус в отдельных колонках READ/WRITE, включая повторы. Сумма её
  строк не является числом запросов. Таблица `Received frames and final call results`
  отдельно показывает полные кадры и итоговые вызовы по терминальным статусам
  с общей строкой итогов. READ включает проверочные чтения.
- `RESPONSE_TYPES`: типы всех полных ответов, включая невалидные кадры и
  валидные отрицательные ответы.
- `WRITE_TOTALS`: вызовы записи `Write calls`, результаты `WRITE_ACK results`,
  совпавшие проверочные чтения RW-параметров `Matching readbacks` и пропущенные
  пары `Skipped ID pairs`. Каждая пара содержит два вызова записи. Каждый вызов может
  включать несколько попыток библиотеки; они учитываются в статистике статусов.

`CYCLE_DONE` отмечает конец отчёта. Подтверждение записи и совпадение прочитанного
значения остаются отдельными результатами.

Этот диагностический проход не задаёт порядок опроса для управления отоплением.
