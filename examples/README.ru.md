# Примеры ESP32OT

[English](README.md)

Каждая папка содержит отдельный Arduino sketch с библиотекой `ESP32OT` из
этого репозитория.

| Пример | Назначение |
| --- | --- |
| [Master](Master/Master.ino) | Синхронный Status, запись TSet и чтение Tboiler; обработка возвращённых результатов в `loop()` |
| [MasterHeap](MasterHeap/MasterHeap.ino) | Выделение и освобождение heap master, перезапуски; [запуск и охват](MasterHeap/README.ru.md) |
| [ReadAll](ReadAll/ReadAll.ino) | Последовательное чтение всех 87 доступных для чтения ID и всех заявленных TSP/записей истории ошибок в `loop()`; вывод статуса ответа и успешных данных; [запуск](ReadAll/README.ru.md) |
| [TestAllIDs](TestAllIDs/TestAllIDs.ino) | Последовательная проверка ID в `loop()`, индексированных данных, карта наблюдаемого доступа и счётчики статусов; запись по умолчанию отключена; [запуск](TestAllIDs/README.ru.md) |
| [MasterCallbacks](MasterCallbacks/MasterCallbacks.ino) | Те же синхронные запросы; обработка и логирование завершений попыток через callback |
| [MasterAsync](MasterAsync/MasterAsync.ino) | Асинхронный Status с минимальным интервалом 750 мс при готовой шине; результат через callback |
| [Slave](Slave/Slave.ino) | Демонстрационный ведомый с Status, TSet, Tboiler и RelModLevel |
| [TransparentProxy](TransparentProxy/TransparentProxy.ino) | Две шины: пересылка запросов термостата котлу и возврат его ответов |

## Выбор примера

Откройте этот репозиторий как проект PlatformIO. В приложенном
[platformio.ini](../platformio.ini) выберите один sketch через `src_dir`:

```ini
[platformio]
src_dir = examples/Master
```

Остальные папки перечислены в том же файле. Выберите окружение под свою плату:
по умолчанию используется `esp32-s3`; также предусмотрены `esp32-s2`,
`esp32-c3`, `esp32` и `esp32-c6`. Окружение `ci` получает идентификатор платы
из `PIO_BOARD`. Конфигурация использует ветку `prep_IDF6` платформы pioarduino:
библиотеке требуются RMT API из ESP-IDF 6. Родительский проект прошивки не нужен.

Все master-примеры, включая `MasterHeap` и `ReadAll`, принимают
`MASTER_RX_GPIO` / `MASTER_TX_GPIO`. `Slave` принимает `SLAVE_RX_GPIO` /
`SLAVE_TX_GPIO`; прокси — обе пары. Имена обозначают роль ESP32: её
master-интерфейс подключён к котлу, slave-интерфейс — к термостату. Профиль S3
задаёт master RX=35 / TX=36; резервные значения sketch — 4/5.
У `Slave` по умолчанию 4/5. У slave-интерфейса прокси по умолчанию GPIO6/7,
либо GPIO18/19 на обычном ESP32, поскольку GPIO6/7 типичных модулей заняты
flash. Выберите GPIO по своей плате и схеме, учитывая USB, flash и другую
периферию. GPIO нельзя соединять с OpenTherm-линией напрямую: нужны
соответствующие электрические интерфейсы.

В `TransparentProxy` каждый GPIO можно независимо переопределить без правки
sketch. Например, добавьте эти определения к существующим `build_flags`
выбранного окружения:

```ini
  -DMASTER_RX_GPIO=4
  -DMASTER_TX_GPIO=5
  -DSLAVE_RX_GPIO=6
  -DSLAVE_TX_GPIO=7
```

Неуказанные определения сохраняют значения по умолчанию. Sketch явно
преобразует числовые значения в `gpio_num_t`.

## Работа master и slave

`Master` и `MasterCallbacks` записывают TSet = 55 °C, при этом разрешение
отопления по умолчанию выключено: `HEATING_ENABLED = false`. Уставка и флаг
разрешения — отдельные значения. Все три master-примера повторяют неудачный
первоначальный запуск из `loop()`. Успешный `begin()` запускает драйвер и worker;
наличие котла подтверждается ответом. После фатальной ошибки драйвера перед
перезапуском может потребоваться явный `end()`. Автоматическое восстановление
после такой ошибки примеры не реализуют.

Начать удобнее с `Master`: `sendRequest()` ждёт завершения и возвращает
самостоятельное значение сообщения. `loop()` выводит raw-запрос, полный ответ
при его наличии и итоговый статус, затем читает успешные результаты.
Синхронные запросы используют `Config::maxAttempts`, по умолчанию 5. `INVALID`,
таймауты и восстанавливаемые ошибки могут повторяться; успешные ACK и валидные
ответы `DATA_INVALID` / `UNKNOWN_DATA_ID` прекращают повторы. Библиотека
сама обслуживает приём, межкадровые паузы и уступает CPU при ожидании, поэтому
отдельный delay callback в этих примерах не нужен.

`MasterCallbacks` отправляет те же синхронные запросы, но `onStatusChange()`
обрабатывает завершение каждой попытки. Лямбда `onRequest()` хранит счётчик
попыток в захвате и выводит исходящий кадр перед TX. Повторы могут дать несколько
записей лога на один `sendRequest()`. Callbacks выполняются внутренним worker; ссылки
на переданные сообщения действительны только во время вызова. Нельзя выполнять
синхронную отправку из callback worker того же экземпляра.

`MasterAsync` отправляет Status с нулевыми master flags без ожидания.
`true` от `sendRequestAsync()` означает принятую команду; её результат приходит
позже через callback. Каждая асинхронная команда делает одну попытку.
`isReady()` учитывает текущий обмен и межкадровую паузу, поэтому отдельный флаг
ожидания и опрос `getResult()` не нужны. Интервал 750 мс задаёт минимальное
время между принятыми запросами; занятая шина может увеличить паузу.

Операция может завершиться без полного ответа, например по таймауту или
ошибке драйвера. `hasFrame()` отличает такие результаты от полных принятых
кадров, но не означает успех. При активном master-запросе корректный по
остальным признакам ответ с другим ID получает статус `INVALID`, а не
`SUCCESS`. Его полный raw-кадр остаётся доступен в `onResponse` и status
callback. Эта проверка ID не применяется к входящим slave-запросам и пассивно
принятым кадрам вне активного обмена.

Корректно принятые `DATA_INVALID` и `UNKNOWN_DATA_ID` имеют собственные
терминальные статусы операции. Это валидные отрицательные ответы: `hasFrame()`
и `isComplete()` возвращают true, а `isSuccess()` — false. Их payload нельзя
интерпретировать как успешно прочитанные данные. `INVALID` обозначает
повреждённые ответы или ответы с несовпадающим ID.

`as<Float>()` создаёт самостоятельную
копию с геттерами f8.8 без выделения heap, RTTI и собственной проверки ID во
время выполнения. Выбирайте обёртку по фактическому формату сообщения;
`get()` декодирует значение, сохраняя raw-данные и метаданные.

`Slave` — модель без управления нагревателем: фактические флаги состояния и
модуляция нулевые, температура подачи фиксирована на 35,5 °C, а записанная
TSet хранится только в RAM. На валидный запрос неизвестного ID возвращается
`UNKNOWN_DATA_ID`; на неподдерживаемую операцию с известным ID —
`DATA_INVALID`. `sendResponseAsync()` передаёт ответ без блокирующего ожидания;
таймингами TX управляет библиотека. Мастер не подтверждает ответ ведомого
отдельным ACK.

## Прозрачный прокси

```text
Комнатный термостат (master)
  <-> OpenTherm-интерфейс slave
ESP32: thermostat -- callbacks -- boiler
  <-> OpenTherm-интерфейс master
Котёл (slave)
```

Нужны два электрических интерфейса и два независимых экземпляра драйвера с
worker. Котловая сторона запускается первой. Каждый приёмный callback сразу
передаёт **копию raw-кадра** другому драйверу. IDs, vendor bits, parity и
отрицательные ответы не пересобираются. Полные кадры с ошибкой parity тоже
пересылаются; неполный захват нельзя переслать как сообщение.
`acceptInvalidRequests` включён только на входе со стороны термостата, чтобы
полные невалидные запросы тоже получали контекст маршрутизации.

Если ID ответа котла отличается от ID активного запроса, он получает статус
`INVALID`, а прокси всё равно пересылает полный raw-кадр без изменений.
Диагностика не фильтрует и не исправляет принятый ответ.

`Message` уже содержит raw-кадр и контекст запроса. Callbacks передают его
напрямую в `boiler.sendRequestAsync(request)` и
`thermostat.sendResponseAsync(response)`. Библиотека сохраняет sequence
на протяжении обмена и отклоняет старые ответы после замены запроса
термостатом. Если котловая шина занята, команда не ставится в очередь.
Прокси не создаёт выдуманные ответы, не повторяет запросы сам и не подменяет
IDs. Решение о повторе после таймаута принимает комнатный термостат.

RMT RX-память выбирается автоматически: один аппаратный блок на драйвер для
C3/C6, два для S3 и один для ESP32/S2. Две шины помещаются без дополнительной
настройки памяти. Каждый драйвер также сохраняет два своих программных RX-буфера.

Раздел 4.3.2 OpenTherm v4.2 требует от gateway начинать пересылку в течение
7 мс после получения сообщения с каждой стороны. RMT сообщает о завершении
после idle 2,5 мс, оставляя часть бюджета на пробуждение и выполнение worker.
**Предел 7 мс не проверен на оборудовании.** Нужны измерения обоих интерфейсов,
включая задержки планировщика и cache. Обычный тайминг ответа slave 20–400 мс
и исключение для gateway описаны в спецификации отдельно.

## Логирование

Прокси выводит raw-кадры во всех четырёх направлениях: `Thermostat -> ESP`,
`ESP -> Boiler`, `Boiler -> ESP` и `ESP -> Thermostat`, со статусами операций.
Status callbacks также выводят каждый новый статус шины, включая таймауты и
ошибки. `onRequest` выводит принятые запросы термостата и исходящие запросы
к котлу; `onResponse` — принятые ответы котла и исходящие ответы термостату.
Исходящие хуки вызываются перед TX с `TRANSMITTING` и `hasFrame() == false`;
входящие содержат полные кадры, включая невалидные. `SUCCESS` после ответа
термостату означает завершение TX; термостат не отправляет ACK.

Для простоты примеров используется прямой `Serial.printf` в callbacks.
Консольный вывод может задерживать worker, поэтому при измерениях и
обеспечении таймингов рабочего gateway стоит вынести логирование из callbacks
пересылки. `Master` выводит логи из `loop()` после возврата `sendRequest()`;
`MasterCallbacks`, `MasterAsync` и `Slave` — из callbacks. Циклы slave и
прокси содержат только `delay(1000)`; workers продолжают обмен.
